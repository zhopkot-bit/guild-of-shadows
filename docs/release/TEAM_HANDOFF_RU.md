## База и ветки

На момент подготовки удалённый `main` — `17d7070`; технический комплект и архитектура — `art/remaining-art-v2`, коммит `1d171da`, PR №16. Локальный `origin/main` ранее отставал: перед созданием рабочей ветки нужно обновить ссылки и записать фактический базовый SHA в PR.

Команды 1, 4 и 6 начинают независимые изменения от актуального `main`. Команда 2 проверяет исправление короля от актуального `art/remaining-art-v2`; команда 5 использует тот же commit для воспроизведения дефекта. Команда 3 готовит арены от `main`, а Брана берёт из отдельного PR №11 с учётом существующей задачи №7. При зависимости от ещё не объединённого PR явно указать эту зависимость; основной разработчик отвечает за перенос в интеграционную ветку.

PR №16 остаётся черновиком. Его наличие и принятый облик не означают закрытие технической приёмки. `main` меняется через проверенные PR; публикация требует отдельного решения владельца.

Принятый арт перерисовывается только по конкретной согласованной правке; исключения из ТЗ записываются явно.

## Формат задания для исполнителя

1. Взять один пакет с ID из `WORK_PACKAGES.json`, проверить зависимости и записать базовый SHA.
2. Указать изменяемые пути, первый проверяемый результат и ограничения доступа.
3. Создать отдельную ветку/PR, сослаться на задачу команды и ID пакета. Сначала доказать проблему; в описании PR указать результат, проверки и оставшиеся ограничения.
4. Не включать в PR соседние пакеты, постороннее форматирование, генерируемые мастера или обновления зависимостей без необходимости.
5. Передать основной команде diff, команды воспроизведения и артефакты именно проверенного commit. Не подменять браузерный тест модульным, тест SDK — заглушкой, реальный телефон — размером окна.

## Интеграция и завершение

Статусы: `ready` → `in progress` → `review` → `verified` → `done`. У блокировки есть причина и владелец следующего действия. `waiting_for_dependencies` означает ожидание перечисленных пакетов, а не запрет подготовительной работы.

Основной разработчик проверяет границы diff и контракты; T5 подтверждает применимые сценарии. Только после этого интегратор объединяет PR и обновляет общий baseline. Работа считается готовой к релизу после всех ворот архитектурного плана, а не после распределения задач.

Состав исполнителей, оценки в человеко-днях и доступность устройств/черновика платформы заполняются при фактическом запуске команд. Пакеты готовы к распределению; календарная дата выпуска пока не назначена.
